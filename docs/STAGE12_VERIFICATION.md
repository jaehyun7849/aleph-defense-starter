# 12단계 실제 결과 확인 절차

이 문서는 학생이 직접 실행한 정상·금지 요청을 한 표로 남기는 절차입니다. 코드와 모의 시험만으로 운영 시험을 통과했다고 기록하지 않습니다. 공식 41종의 세부 목록은 운영 측 명세를 사용합니다. 아래 1~11단계 점검 목록은 공식 41종 목록을 대신하지 않습니다.

## 역할과 준비

- 코드 담당: 기존 작전실의 요약과 가린 기록 일치 검사, 자료 비노출, 설치·실행·중지·복구 안내, 검증 양식을 유지합니다.
- 학생: 기존 Supabase/Vercel 설정을 직접 확인하고 배포, A/B 계정 로그인, 페이지 승인, 실제 요청과 공식 심판 시험을 실행합니다. 비밀번호·키·사용자 번호·사본 원문을 채팅이나 Git에 복사하지 않습니다.
- `git log -1 --format="%H %s"`의 커밋과 배포 `/aleph.json`의 commit, step 12를 먼저 대조합니다. 불일치하면 현재 코드의 결과로 기록하지 않습니다.
- [작전실 준비](OPERATIONS_ROOM.md)에 따라 감사 테이블이 없을 때만 SQL을 적용합니다. 기존 메모·계정·승인·감사 기록은 삭제하지 않습니다. 엔진 연결이 없으면 6~9단계의 실제 엔진 검증은 미실행입니다.

## 한 표에 남기는 방법

1. [STAGE12_RESULTS.csv](STAGE12_RESULTS.csv)를 비공개 작업 위치에 복사합니다. 표 전체는 같은 검사 커밋·배포를 기준으로 작성합니다. 재배포하면 별도 표를 만듭니다.
2. `status`는 `not_run`(미실행), `passed`(실측 일치), `failed`(실측 불일치), `unavailable`(요청했으나 결과 확인 불가)로 구분합니다. 기대 결과만으로 통과를 채우지 않습니다.
3. 브라우저 개발자 도구 Network에서 해당 요청의 메서드·경로·HTTP 상태·고정 사유 코드만 확인합니다. 쿼리·개별 메모 ID는 가리고, 요청/응답 본문·인증 헤더·HAR·Copy as cURL은 저장하지 않습니다. 응답을 기록할 때 자료 내용 대신 `자료 반환 없음`, `허용된 자료 확인`만 적습니다.
4. 엔진의 실제 `requestId` 또는 서버가 제공한 요청 추적 ID가 있으면 `request_id`에 기록합니다. 없으면 `미제공`으로 적습니다. 임의 UUID를 만들지 않고, 데모 승인 번호나 작전실 감사 행 ID·snapshotId를 API 요청 ID로 바꿔 적지 않습니다. 시각은 실제 확인한 ISO 8601 시각으로 적습니다.
5. `evidence_ref`에는 비공개 증빙의 가명 번호만 적습니다. 개인정보가 없는 가린 화면과 서버 기록을 같은 요청 ID·시각으로 대조합니다. 단순 HTTP 2xx가 아니라 아래 기대 조건 전체를 확인합니다.
6. 정상과 금지 요청을 모두 실행합니다. 기존 `/owner-check.html`은 현재 페이지 승인을 지원하는지 먼저 확인합니다. 승인 연결이 없어서 막힌 시험은 통과로 쓰지 않고, 승인된 기존 자료실의 요청 또는 운영 측 공식 시험 도구를 사용합니다. 인증 헤더를 콘솔·터미널에 복사하지 않습니다.

## 1~11단계 요청 목록

| 단계 | 정상 요청과 기대 결과 | 금지 요청과 기대 결과 | 실행 위치 |
|---|---|---|---|
| 1 | 자료실 첫 화면 GET → 정상 화면 | 현재 배포의 공개 data.json GET → 메모 0건 또는 404, SAMPLE_NOTE_1 노출 없음 | 자료실/시크릿 창 |
| 2 | 로그인·승인 후 본인 메모 목록 GET → 허용된 자료 확인 | 무로그인 목록/개별 GET → 401/403, 자료 없음 | 자료실/시크릿 창 |
| 3 | 등록한 시험 계정으로 로그인 후 본인 요청 허용 | 로그인 없음/잘못된 토큰 → 401, 자료 없음 | 기존 로그인 화면/공식 시험 도구 |
| 4 | 최종 자료 API로 본인 자료 조회 허용 | 브라우저 역할로 원본 DB 직접 CRUD → 권한 거부 | 기존 자료실/공식 DB 권한 점검 |
| 5 | 허용된 최종 경로로 본인 임시 메모 CRUD 성공 | 타인 조회 404, 소유자 변경 403, 허용되지 않은 경로 거부; 공개 코드 서버 키 없음 | 승인된 자료실/공식 시험 도구 |
| 6 | 실제 엔진의 등록 기기 요청 allow | 실제 엔진의 미등록 기기 요청 거부, 자료 없음 | 연결된 ALEPH 엔진 |
| 7 | 정상 요청·실제 추가 확인 후 새 요청 allow | 계약의 복합 이상 요청 step_up, 확인 전 자료 없음 | 연결된 ALEPH 엔진 |
| 8 | 본인 구역 요청 allow | 타인 메모·다른 반·학생 공지 수정·기능 경로 deny | 연결된 ALEPH 엔진 |
| 9 | 정상 사건 observe, 정상 접근 유지 | 계약의 폭주 사건 제안과 실제 회수 확인, 회수 후 재접속 거부 | 운영 사건·회수 도구 |
| 10 | 검증 사본으로 지정 B 메모 한 건 복구 후 ID·소유자·내용 해시 일치 | 잘못된 계정/대상/변조 사본은 쓰기 전 거부, 다른 자료·감사 보존 | 비공개 복구 설정/인증된 호출 수단 |
| 11 | 현재 페이지 서버 승인 후 자료 조회; 설치 앱에서도 동일 | 미승인·취소 후 조회 거부, 설치 표시만으로 열리지 않음, 오프라인 API 자료 없음 | 기존 자료실/관리자 승인 창/설치 앱 |

복구의 실제 실행은 학생이 사전 검토한 사본과 인증된 호출 수단을 준비했을 때만 합니다. [복구 안내](NOTE_RESTORE.md) 및 README의 중지·복구 순서를 따릅니다. 시험 때문에 원본 DB 권한을 풀거나 자료실 전체를 삭제하지 않습니다.

## 작전실과 공식 시험

관리자 로그인 → 현재 페이지 승인 → **탈환 작전실 → 서버 요약 새로고침 → 수치 대조용 가린 서버 기록**을 엽니다. 같은 응답의 snapshotId·observedAt과 최대 최근 100건 범위를 확인합니다. 규칙은 서버 구현 목록이며 실행 횟수가 아닙니다. 기록의 demo_revocation 수와 데모 접속 취소 건수, note_restore 수와 복구 건수·최신 가린 버전을 대조합니다. 실제 탐지·기기 회수·정책 복구가 미연결이면 미실행, 감사 조회 실패면 확인 불가여야 합니다. 화면에 메모 본문이 나오면 실패입니다.

첨부한 기존 심판 화면에는 무인증 조회·타인 메모 연속 전송 공격이 통했다고 표시되어 있습니다. 이는 과거 제출의 실패 증거이며 현재 커밋 통과 증거가 아닙니다. 같은 금지 요청을 현재 배포에서 다시 확인하고 공식 심판을 재실행해야 합니다. 새 실행 전에는 기존 결과를 해결됨으로 바꾸지 않습니다.

공식 41종은 실행 전 모두 미실행입니다. 운영 측 도구의 실제 결과에서 시험별 ID·기대 결과·관측 결과·요청 ID·확인 시각을 같은 CSV 열에 추가하고 `kind`를 `official_41`로 구분합니다. 공개 41종 목록이 없으므로 임의 시험 이름이나 결과를 생성하지 않습니다. 일부만 실행했으면 나머지는 미실행으로 둡니다.

## 제출 저장점

1. 실제 기록과 배포 커밋을 대조하고 `git status --short` 및 포함 파일의 비밀값 검사를 확인합니다. 실측 CSV 원본·토큰·본문·사본·bundle-notes.json·artifacts/submission.json은 커밋하지 않습니다.
2. 일반 커밋 제목 `12단계 저장점`으로 저장한 다음 해당 커밋을 배포합니다. 이후 다른 파일 변경이 없는 상태에서 `npm run bundle`을 실행합니다. `bundle-notes.json`은 학생이 비밀값 없이 이번 작업 설명을 적는 로컬 입력입니다.
3. 생성 JSON의 commit, step, changedFiles와 자기 점검 결과를 확인합니다. 자동 GET 자기 점검은 인증된 정상 요청이나 공식 41종 시험을 대신하지 않으며 복구/승인 POST의 not_run도 그대로 남깁니다. 첫 오류가 나면 그 오류 한 가지를 먼저 해결합니다.
