# 기존 자료실의 서버 승인 데모

별도 가상 자료실로 이동하지 않습니다. 기존 첫 화면의 로그인·기기 승인 요청·승인 결과 확인·메모 조회/추가/수정/삭제를 그대로 사용합니다. 서버가 현재 페이지 접속을 승인하는 데모이며 하드웨어 기기 서명이나 운영 엔진의 실제 기기 증명은 아닙니다.

## 준비

1. Supabase SQL Editor에서 docs/DEMO_APPROVAL.sql을 한 번 실행합니다. 이미 이전 데모 설정 때 실행했다면 다시 실행할 필요가 없습니다. 기존 notes 테이블은 변경하지 않습니다.
2. Vercel 환경변수 DEMO_APPROVAL_ADMIN_IDS에 관리자 계정의 Supabase User UID를 등록합니다. 여러 UID는 쉼표로 구분합니다. 기존 SUPABASE_URL/SUPABASE_SECRET_KEY 서버 설정을 사용하며 공개 코드에 키를 넣지 않습니다. 이전에 등록한 값은 그대로 재사용합니다.
3. 수정 PR을 main에 반영하고 새로 배포합니다. 이 구현에서는 실제 DB 설정·배포·로그인 시험을 실행하지 않았습니다.

## 기존 화면에서 체험

1. 운영 사이트 첫 화면에서 로그인하고 **기기 승인 요청**을 누릅니다. 화면은 대기 상태와 요청 번호를 표시하고 기존 메모는 숨겨져 있습니다. 설치 표시나 버튼 클릭만으로 승인되지 않습니다.
2. 별도 창에서 운영 사이트 주소 끝에 **/demo-approval.html**을 붙여 관리자 화면을 엽니다. 첫 화면에는 별도 데모 이동 링크가 없습니다.
3. 관리자 계정으로 로그인하고 **관리자 승인 목록 확인**을 누릅니다. 첫 화면의 요청 번호를 찾아 **관리자 승인**을 누릅니다. 같은 계정을 관리자로 등록해 두 역할을 체험할 수도 있습니다. 관리자 화면에서는 새 승인 요청을 만들지 않습니다.
4. 원래 자료실에서 **승인 결과 확인**을 누르면 기존 메모가 열립니다. 추가·수정·삭제도 기존 API를 사용합니다. 다른 사람의 메모에 접근할 권한을 주지는 않습니다.
5. 관리자가 승인 취소를 누르면 다음 결과 확인 또는 자료 요청은 차단되고 화면이 잠깁니다. 화면에 이미 표시된 내용은 서버 상태를 다시 확인할 때 지워집니다. 취소 후 재요청은 새로고침하고 로그인한 뒤 진행합니다.
6. 새로고침·새 탭·로그아웃 후에는 새 승인이 필요합니다. 로그인 토큰과 데모 접속 핸들은 페이지 메모리에서만 사용합니다. 계정당 활성 요청은 하나이며 새 요청은 이전 페이지 요청을 대체합니다.

## 서버 경계와 계약

- POST /api/demo-device + action=request: 서버가 pending을 저장합니다. 생성한 sessionToken은 현재 페이지에서만 보관하며 DB에는 해시만 저장합니다.
- GET /api/demo-device: 서버가 검증한 학생 로그인과 X-Demo-Session에 묶인 unregistered/pending/approved/revoked 상태를 반환합니다.
- POST /api/demo-device + action=list/approve/revoke: 서버 환경변수에 등록된 관리자 계정만 처리할 수 있습니다. approve/revoke에는 requestId를 보냅니다.
- 기존 /api/notes, /api/notices, /api/restore-note는 서버 승인 기록을 검사한 뒤 기존 소유자·강사·복구 권한 검사를 실행합니다. 승인만으로 기존 권한 거부를 무효화하지 않습니다.
- 관리자 설정·저장소·로그인 검증 실패는 허용하지 않습니다. 클라이언트의 approved, role, deviceRegistered 값은 승인 근거가 아닙니다.
- 별도 /api/demo-notes와 가상 메모 화면은 제거했습니다. /demo-approval.html은 관리자 승인 화면입니다. /api/device-approval의 공식 엔진 연결은 미구현이며, 기존 화면에서는 데모 전용 상태 API를 사용합니다.

기존 자료를 대상으로 페이지 접속 승인을 시연합니다. 실제 하드웨어 기기 인증이나 공식 심판 통과를 주장하지 않습니다. 추가 SQL이나 새로운 환경변수는 필요하지 않습니다.
