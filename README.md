자료실 복구 API 서비스의 경로는 **POST /api/restore-note**입니다. 기존 메모 주소와 화면 메뉴는 보존합니다. 서버에 등록한 시험 계정 B만 호출할 수 있고, 서버 비공개 사본의 지정 ID 한 건만 복원합니다. 요청의 id·ownerId·contentSha256과 사본을 대조하고 결과도 같은 세 항목으로 검증합니다. 다른 메모와 감사 테이블을 수정하거나 삭제하지 않습니다. 제출 설정의 restoreRoute는 구현된 경로 문자열 /api/restore-note이며 allowedRoutes의 POST 항목과 일치합니다. 10단계 배포 정보 aleph.json에도 복구 경로를 표시합니다. 공개 실습 저장소의 경로 문자열 사용례를 참고한 등록이며 공식 심판의 요청 본문 계약과 실제 연결 성공은 아직 미확인입니다. 현재 설정 단계는 11입니다.

비공개 환경변수 VAULT_RECOVERY_TEST_B_ID, VAULT_NOTE_BACKUP, VAULT_NOTE_BACKUP_SHA256을 운영자가 공식 서버 설정에 넣어야 합니다. 실제 사본·키·시험 계정 정보를 Git이나 답변에 넣지 않습니다. 사본 미제공·검증 실패는 중단합니다. 해시는 사본 무결성을 검증하며 사본의 안전성은 사전 검토가 필요합니다. [형식과 시험 방법](docs/NOTE_RESTORE.md).

`node --test test/note-restore.test.mjs`는 시험 B의 가상 메모만 복원해 ID·소유자·내용 해시 일치와 다른 메모·감사 보존을 확인합니다. 실제 B 로그인·비공개 사본·운영 DB 복원·공식 심판은 아직 미실행입니다.


저장점 재실행: `node --test test/policy-preview.test.mjs test/policy-restore.test.mjs test/note-restore.test.mjs`로 안전 사본 검증·격리 정책 복원·시험 B 한 건 복원을 가상 자료로 확인합니다. 미리보기는 변경하지 않고, 복원은 확인한 계획 지문이 있어야 실행합니다. 사본 누락·검증 실패·다른 소유자는 거부되어야 합니다. 화면 메뉴 변경은 없습니다. 실제 사본 복구·배포·복구 후 1~9단계 실측·공식 심판은 미실행입니다. `npm run bundle`의 무로그인 복구 POST 점검은 실제 배포의 응답만 기록하며 인증된 복구는 실행하지 않습니다.

## 10단계 복구 경로 등록 및 실행 직전 재검증

2026-10-14 로컬 시험: 복구 관련 5건 통과. 전체 단위 시험은 53건 중 50건 통과·2건 실패·1건 미실행이며, 시작 틀 API 기준표 및 XDR 실행기 시험의 두 실패는 변경 전에도 재현됩니다. 실제 심판 통과 증거는 아닙니다. 직접 확인: `node --test test/note-restore.test.mjs`. 가상 시험에서 변조·삭제된 B 메모는 ID·소유자·내용 해시가 일치하도록 복구되어야 하며, 조회 도중 사본이나 검증값이 사라지거나 변경되면 DB 쓰기 0건이어야 합니다. 화면 메뉴 변경은 없습니다. 재배포 뒤 /aleph.json의 restoreRoute와 무로그인 POST의 401/login_required를 확인합니다. 실제 B 복구와 공식 심판 재제출은 미실행입니다.

## 10단계 복구 뒤 1~9단계 재검증 순서

아래는 앞으로 실제 복구 후 실행할 순서입니다. **실제 안전 사본과 실제 B 계정 자료로 복구한 뒤의 재검증은 현재 모두 미실행**입니다. 기존 가상 파일/모의 SDK 시험의 통과를 이 표의 통과로 옮겨 적지 않습니다. 정책 복원은 격리 시험 폴더의 메모 권한 파일 한 개, 자료 복원은 지정 B 메모 한 건으로 범위를 한정합니다.

1. **안전 사본과 실행 대상 확인.** 사전 검토 기록의 안전 버전·별도 SHA-256을 확인하고 `npm run policy:preview` 및 확인값 없는 `npm run policy:restore`에 실제 사본·시험 폴더 인수를 전달합니다. 사용 형식은 [미리보기](docs/POLICY_PREVIEW.md)와 [시험 복원](docs/POLICY_RESTORE.md)을 따릅니다. 버전·변경 파일·줄 범위·보존 파일·감사 기록을 확인합니다. 사본 누락·해시/버전 불일치·운영 폴더이면 중단합니다.

2. **확인한 시험 정책만 복원.** 표시된 `planSha256`을 확인해 같은 명령에 `--confirm`으로 전달합니다. `applied: true`와 시험 폴더의 메모 권한 파일 해시가 안전 사본과 같은지 확인합니다. 다른 서비스 파일과 기존 감사 기록의 기존 부분이 그대로인지 대조하고 새 복원 감사 항목만 추가됐는지 확인합니다. 새 Node 프로세스를 사용해 이전에 로딩한 정책 캐시를 재사용하지 않습니다. 운영 정책을 되돌렸다고 기록하지 않습니다.

3. **시험 B 자료 한 건 복구·대조.** 비공개 검토 사본이 준비된 환경에서 인증된 시험 B로 `POST /api/restore-note`를 호출합니다. 본문은 등록한 대상의 id·ownerId·contentSha256 세 값만 사용합니다. 성공 응답 세 항목을 사본과 대조하고, B의 기존 `GET /api/notes/:id`로 다시 읽어 같은 ID·사본 소유자·내용 해시인지 확인합니다. 내용 해시는 NOTE_RESTORE.md의 title/body 순서로 메모리에서 계산하며 본문을 출력하거나 기록하지 않습니다. 다른 메모와 기존 감사 기록도 그대로인지 대조합니다. 로그인·서버 설정·사본이 준비되지 않으면 미실행으로 남깁니다.

4. **1~2단계 공개 자료·화면 점검.** 현재 보호된 자료실 화면이 열리고 정상 로그인 화면이 유지되는지 확인합니다. 시크릿 창의 `/data.json`은 메모 0건 또는 404여야 하고 초기 공개 확인 표시가 없어야 합니다. 비로그인 `/api/notes` 및 개별 메모 조회는 401/403 JSON 오류이며 자료가 없어야 합니다. 실제 자료가 보이면 다음 단계로 넘어가지 않습니다.

5. **3~5단계 로그인·최종 API·원본 DB 점검.** 배포된 `/owner-check.html`에서 서로 다른 A/B 시험 계정으로 「임시 메모로 점검 시작」을 누릅니다. 본인 생성·목록·조회·수정·삭제는 성공, 무로그인은 401, 타인 메모 접근은 404, 소유자 변경은 403이어야 합니다. 이 화면은 새 임시 메모를 시험하므로 3번의 복구 대상 한 건 대조를 대신하지 않습니다. 공식 DB 설정에서 기존 anon/authenticated 직접 CRUD 권한 회수가 유지되는지 확인합니다. 화면·공유 모듈에 서버 키가 없어야 하며 DB를 공개해 정상 동작을 맞추지 않습니다. 원본 DB 역할 점검을 하지 않았다면 별도 미실행입니다.

6. **6~8단계 판정기 정상/금지 요청 재검증.** 복원한 시험 폴더의 `src/decider.mjs`를 직접 불러와 아래 명령을 실행합니다. `<복원한 시험 폴더>`에는 실제 격리 폴더를 넣습니다. 현재 자료실 폴더에서 실행하며, 기본 판정기로 대체해 시험하지 않습니다.

```powershell
$env:ALEPH_TRIAL_DIR = '<복원한 시험 폴더>'
@'
import { resolve, join } from 'node:path';
import { pathToFileURL } from 'node:url';
import { checkDecider } from './scripts/decider-test.mjs';
if (!process.env.ALEPH_TRIAL_DIR) throw new Error('trial_directory_required');
const { decide, RULE_IDS } = await import(pathToFileURL(join(resolve(process.env.ALEPH_TRIAL_DIR), 'src/decider.mjs')));
const results = await checkDecider({ decide, ruleIds: RULE_IDS });
for (const item of results) console.log(`${item.passed ? '통과' : '확인 필요'} · ${item.name}`);
if (results.some(item => !item.passed)) process.exitCode = 1;
'@ | node --input-type=module
Remove-Item Env:ALEPH_TRIAL_DIR
```

정상 등록 기기와 A 자기 메모는 allow, 미등록은 deny/device_not_registered, 복합 이상은 step_up/step_up_required, 유효한 모의 추가 확인 뒤 요청은 allow여야 합니다. B의 A 메모·다른 반·학생 공지 수정은 deny/resource_forbidden, export 같은 기능 경로는 deny/resource_not_allowed여야 합니다. 실제 엔진의 등록 기기·재로그인 시각 검증·자료 전달 보류가 연결된 환경에서만 실제 차단/재허용도 확인합니다. 가상 사건 통과를 실제 재로그인·기기 검증으로 기록하지 않습니다. 실제 공지/강사 시험은 별도 서버 등록이 있어야 하며 없으면 미실행입니다.

7. **9단계 탐지 재검증.** 복원한 시험 폴더에 보존한 detect.mjs와 해당 detect-test.mjs/시험 실행기가 준비된 상태에서 `npm run detect:test`를 실행합니다. 제공 v1의 정상 30건·120건·사용자 분산·시간 분산은 observe, 10분 내 121/200건은 propose_revocation/burst_read/subject여야 합니다. 별도 로컬 확장은 낯선 네트워크와 조회 폭주가 함께일 때만 한 기기의 제안을 내고 정상·지역 단독·기기 미확인은 observe여야 합니다. 실제 회수·재접속 차단·경과 시간은 심판 또는 연결된 검증 엔진에서만 확인하고 미실행 항목을 남깁니다. 시험 폴더에 실행기가 없으면 원래 자료실 시험으로 대체하지 않습니다.

8. **기록 및 제출 점검.** 실행한 날짜·정책 버전·사본 해시·복구 한 건의 메타데이터 일치 여부·시험 이름·HTTP 상태/사유·통과/실패/미실행만 기록합니다. 토큰·비밀번호·개인키·실명·메모 본문은 기록하지 않습니다. 첫 실패가 있으면 그 항목을 해결하기 전 통과로 표기하지 않습니다. 저장점 커밋·승인된 배포 후 `npm run bundle`의 실제 HTTP 결과와 배포 커밋을 확인합니다. JSON 생성 성공과 모든 점검 통과는 구별합니다.

| 복구 후 확인 항목 | 정상 결과 | 금지/실패 결과 | 현재 실제 복구 후 상태 |

기존 확인 기록: 가상 정책 복원 시험 3건과 B 메모 모의 복구 시험 3건은 통과했습니다. 이것은 위의 실제 복구 후 재검증 표와 별개입니다. 이번 README 절차 작성에서는 새로운 복원·DB 요청·배포·심판 시험을 실행하지 않았습니다.

네트워크·기기 항목이 있는 [로컬 확장 사건](docs/DETECT_EVENTS.md)은 기존 복합 조건을 유지합니다. 같은 가명 사용자·등록 확인된 기기별 GET 120건 초과와 해당 10분 구간의 낯선 네트워크가 함께 맞을 때만 기기 ID를 포함해 제안합니다. 지역·조회량 단독·등록 확인 누락은 observe입니다. 확장 정보가 불완전하거나 두 형식이 섞인 입력은 v1으로 완화하지 않습니다. 메모·토큰·실명·실제 IP는 기록하지 않습니다. 기존 decide 응답과 API는 그대로입니다.

## 학생이 하는 일: 세 걸음

1. GitHub 계정을 만듭니다.
2. 방어전 1단계 카드의 **Deploy** 버튼을 누릅니다. Vercel에 GitHub로 로그인하고, 새 저장소가 **본인 계정의 Public 저장소**인지 확인한 뒤 Deploy를 누릅니다.
3. 배포가 끝나면 화면에 나온 `https://…vercel.app` 주소를 방어전 1단계 카드에 붙여넣고 제출합니다. 저장소 주소나 설정 파일은 적지 않습니다.

배포가 끝나면 `/`에서 점령된 가상 자료실을 볼 수 있습니다. `/data.json`에는 같은 가상 메모가 공개됩니다. 이 공개 상태를 확인하는 것이 1단계의 출발점입니다. 1단계 접수와 심판 판정은 포털에서 확인합니다.

## 시작 틀의 자동 처리

`vercel.json`은 정적 결과물 `public`을 배포합니다. 빌드 명령 `npm run build`는 Vercel이 제공하는 GitHub 저장소 소유자·이름, 커밋 SHA, 배포 URL을 검증하고 `public/aleph.json`을 생성합니다. 이 값이 없으면 빌드가 실패하므로, 성공한 것처럼 빈 주소를 내보내지 않습니다. `aleph.json`의 내용만으로 저장소 소유권이나 방어 성공을 인정하지 않습니다. 심판이 공개 저장소의 실제 커밋과 배포된 자료를 따로 대조해야 합니다.

`aleph.config.json`의 `repoUrl`과 `publicAppUrl`은 이전 제출 묶음 방식의 자리표시자입니다. 1단계에서는 학생이 편집하지 않습니다. 2단계 이후 코딩 도구가 필요한 설정과 보호 기능을 단계별로 작성합니다. `npm run bundle`과 `bundle-notes.json`도 1단계의 세 걸음에는 포함되지 않습니다.

로컬에서 가상 화면만 확인할 때는 `npm run build -- --local`을 사용합니다. 로컬 실행은 Vercel 배포나 심판 접수를 증명하지 않습니다. 저장소의 `src/attack-check.mjs`는 실제 배포가 된 뒤 `/data.json`을 비로그인으로 요청해 공개 가상 메모의 확인 표시를 읽습니다.

## 다음 단계의 코딩 도구에 전달할 규칙

[AGENTS.md](AGENTS.md)를 먼저 읽히고 한 번에 한 제작 단위만 요청하세요. 2단계부터는 자료 보호를 구현할 때 `public/data.json`을 복사하는 1단계 빌드 흐름도 함께 바꿔야 합니다. 3단계 이후의 로그인, 허용 경로, 5단계의 원본 API 주소, 6단계 이후 정책 규칙은 해당 단계 원고와 계약에 맞춰 추가합니다. 비밀번호·토큰·서버 전용 키·실제 학생 기록을 코드, Git, 제출 묶음에 넣지 않습니다.

`src/decider.mjs`와 `src/detect.mjs`의 로컬 시험은 반 엔진이나 운영 심판의 결과가 아닙니다. 1단계 이후 제출 묶음 계약 `aleph.defense.submission.v2`는 `scripts/bundle.mjs`에 남아 있으며, 코딩 도구가 해당 단계의 최신 배포 주소와 Git 원격을 맞춘 뒤 사용합니다.
